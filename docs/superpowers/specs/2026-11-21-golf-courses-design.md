# 골프장 등록 기능 설계

작성일 2026-11-21 · 상태: 승인 대기

## 의도와 이유

GREENFIELD는 베트남 거주 한인 골프 동호회용 랭킹 앱이다. 현재 라운드를 열 때
고를 수 있는 골프장이 화면에 하드코딩된 한국 4곳(베어즈베스트 청라, 남서울CC,
스카이72 오션, 부여CC)뿐이라 실사용이 불가능하다.

회원이 실제로 치는 베트남 골프장을 고를 수 있어야 하고, 목록에 없는 곳은
회원이 직접 추가할 수 있어야 한다. 추가된 골프장은 모든 회원에게 보이는
공용 목록으로 쌓인다. 관리자가 나중에 점검해서 이름·파·지역을 바로잡고
중복을 통합한다.

공용 목록으로 가는 이유: 동호회 랭킹 앱이라 "어느 골프장에서 많이 치나",
"코스별 평균 타수" 같은 집계가 결국 필요해진다. 각자 자유 텍스트로 적게 두면
"다낭CC / 다낭 골프클럽 / 몽고메리"처럼 제각각 쌓여 나중에 정리가 불가능하다.

## 목표

- 베트남 주요 골프장을 사전 입력해 바로 고를 수 있게 한다
- 목록에 없으면 회원이 그 자리에서 추가하고, 즉시 라운드를 열 수 있다
- 추가된 골프장은 전 회원에게 공유된다
- 관리자가 이름·지역·파·홀수를 수정하고, 중복을 통합하고, 잘못된 항목을 숨긴다
- 라운드의 파를 선택한 골프장 값으로 저장한다 (핸디 계산 정확도)

## 비목표

이번 작업에 넣지 않는다. 필요해지면 별도로 다룬다.

- 코스 레이팅(CR)·슬로프
- 홀별 파 데이터 (클라이언트의 `PAR` 배열은 파72 기준 그대로 둔다)
- 사전 승인 큐 — 승인 대기 때문에 라운드를 못 여는 쪽이 더 불편하다
- 회원 정지, 라운드 무효화 등 그 밖의 관리자 기능
- 티박스별 파·거리
- 골프장 사진, 위치 좌표, 연락처

## 안티목표

기술적으로 동작해도 이렇게 되면 실패다.

- 라운드 열기 단계가 늘어나거나 느려지는 것. 지금은 탭 두 번이면 열린다
- 관리자만 골프장을 추가할 수 있게 되는 것. 등록 권한은 전 회원에게 있다
- 중복이 쌓이기만 하고 정리할 방법이 없는 것
- 회원이 자기를 관리자로 만들 수 있는 것

## 제약

- Supabase 무료 플랜 + GitHub Pages 정적 호스팅. 서버 코드 없음
- 기존 스키마 설계 원칙: 쓰기는 전부 SECURITY DEFINER 함수로. 클라이언트의
  직접 INSERT/UPDATE는 차단
- 핸디 차등은 `gf_confirm_round()`에서 `v_diff := v_gross - r.par`로 계산한다.
  즉 `gf_rounds.par`가 핸디에 직접 영향을 준다
- 현재 클라이언트는 `gf_create_round(p_course, 72)`로 파를 72 고정 전송 중
- 주 사용 환경은 폰이다. 관리 작업도 폰에서 끝나야 한다
- DB 마이그레이션은 사용자가 Supabase SQL Editor에 직접 붙여넣어 실행한다.
  Claude는 DB에 접근할 수 없다

## 접근 방식

관리자가 어디서 수정하느냐를 두고 세 가지를 검토했다.

**A. Supabase 대시보드에서만** — 앱에 관리자 기능 없음. 테이블 에디터에서 행을
직접 수정. 추가 코드가 거의 없고 가장 빨리 끝난다. 그러나 노트북이 필요하고
폰에서 대시보드를 쓰는 것은 상당히 불편해서, 실제로는 방치될 가능성이 높다.

**B. 코스 선택 화면에 관리자 편집 (채택)** — 관리자로 로그인하면 목록의 각
항목에 편집 버튼이 뜬다. 이름·지역·파·홀수 수정, 숨김, 중복 통합을 그 자리에서
한다. 라운드를 열다가 잘못된 항목을 발견하는 순간이 곧 고치는 순간이라
실제 운영 흐름과 맞는다.

**C. 별도 관리자 탭** — B에 더해 회원 정지, 라운드 무효화까지. 지금 필요하지
않은 것까지 묶여 코스 작업이 늦어진다. README의 "남은 과제" 1번이며 나중에
별도로 붙인다.

사용자가 B를 선택했다.

## 결정 사항

### 데이터 모델

`gf_courses` 테이블을 새로 만든다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | uuid PK | |
| `name` | text not null | 표시 이름. 2~40자 |
| `name_key` | text unique | 중복 방지용 정규화 키. 생성 컬럼 |
| `region` | text not null | 북부 / 중부 / 남부 / 기타 |
| `par` | int not null default 72 | 27~80 |
| `holes` | int not null default 18 | 9, 18, 27, 36, 54 |
| `status` | text not null default 'active' | active / hidden / merged |
| `merged_into` | uuid null | 통합 대상 |
| `created_by` | uuid null | 등록자 |
| `created_at` | timestamptz | |

`name_key`는 생성 컬럼으로 둔다. 영숫자·한글 외 문자를 제거하고 소문자화한
값이며 unique 제약이 걸린다. "Montgomery Links"와 "montgomery links"는 같은
것으로 잡히지만 "몽고메리"와 "몽고메리 링크스"는 다른 것으로 남는다. 완전한
중복 방지는 불가능하므로 나머지는 관리자 통합으로 처리한다.

`gf_rounds`에 `course_id uuid references gf_courses(id)`를 추가한다. 기존
`course text`는 그대로 두고 라운드 당시의 이름 스냅샷으로 쓴다. 집계는
`course_id` 기준으로 하므로 나중에 관리자가 이름을 고치거나 중복을 통합해도
과거 라운드가 올바른 골프장에 묶인다.

### 관리자 권한

`gf_profiles`에 `is_admin boolean not null default false`를 추가한다.

기존 컬럼 단위 권한이 이미 `grant insert (id, name, region, hcp)` /
`grant update (name, region)`로 제한되어 있어, 클라이언트는 `is_admin`을
쓸 수 없다. 첫 관리자는 사용자가 Supabase 대시보드에서 직접 지정한다.
읽기는 기존 `p_prof_read` 정책으로 가능하므로 앱이 자기 `is_admin`을 읽는다.

관리자 지정을 앱 안에서 하는 기능은 넣지 않는다. 권한 상승 경로를 만들지
않는 편이 안전하고, 관리자는 어차피 드물게 바뀐다.

### RPC

전부 SECURITY DEFINER. 기존 스키마 관례를 따른다.

- `gf_add_course(p_name, p_region, p_par, p_holes) returns gf_courses`
  프로필이 있고 정지되지 않은 회원이면 호출 가능. 같은 `name_key`가 이미
  있으면 오류 대신 **기존 행을 그대로 반환한다**. 회원 입장에서는 "이미
  있네" 하고 그걸 쓰면 되므로 실패로 다룰 이유가 없다.
  남용 방지로 1인당 하루 10개로 제한한다.
- `gf_update_course(p_id, p_name, p_region, p_par, p_holes, p_status)`
  `is_admin`만 호출 가능. null로 넘긴 항목은 변경하지 않는다.
- `gf_merge_course(p_from, p_into)`
  `is_admin`만. `p_from`을 status='merged', merged_into=p_into로 바꾸고
  해당 골프장을 참조하는 `gf_rounds.course_id`를 `p_into`로 옮긴다.
- `gf_courses` 조회는 RPC 없이 `authenticated`에게 select 권한을 준다.
  읽기 전용이고 민감하지 않다. status='active'만 보이도록 앱에서 거른다.

`gf_create_round`의 시그니처를 `(p_course_id uuid)`로 바꾼다. 함수 안에서
골프장을 조회해 `course`(이름 스냅샷), `course_id`, `par`, `holes`를 채운다.
파를 클라이언트가 보내지 않게 되므로 조작 여지가 사라진다. 기존
`(text,int)` 버전은 제거하고 같은 배포에서 클라이언트를 함께 올린다.

### 화면

**코스 선택** — 기존 하드코딩 버튼 자리를 대체한다.

- 상단에 검색 입력. 이름으로 즉시 필터
- 지역(북부/중부/남부/기타)으로 묶어 표시. 각 항목에 `파 72 · 18홀` 부기
- 최근에 자신이 라운드한 골프장을 맨 위에 따로 보여준다. 매번 검색하지
  않게 하려는 것이며, 안티목표(라운드 열기가 느려지는 것)에 대한 대응이다
- 목록 하단에 `+ 골프장 추가`

**골프장 추가 폼** — 이름, 지역(select), 파(기본 72), 홀수(기본 18).
저장하면 바로 선택된 상태가 되어 이어서 라운드를 열 수 있다.

**관리자 편집** — `A.profile.is_admin`일 때만 각 항목에 편집 버튼이 보인다.
수정 폼은 추가 폼과 같은 필드에 `숨김` 토글과 `다른 골프장으로 통합`
(대상 선택) 이 더해진다.

### 사전 입력 데이터

조사한 베트남 주요 골프장 약 30곳을 권역별로 넣는다. 한인 이용이 많은 곳
위주이며, 확인한 범위에서 전부 파 72다. 홀수는 36·27홀 코스가 섞여 있으나
라운드는 18홀 기준이므로 `par`는 18홀 기준 72로 넣고 `holes`에 실제
규모를 적는다.

북부(하노이 권역)를 가장 두껍게 채운다. 사용자가 삼성 협력사 쪽 업무로
북부에 있고, 회원 분포도 그쪽일 가능성이 높다.

## 빌더 재량

- 검색 필터를 클라이언트에서 할지 서버에서 할지 (목록이 수십 개 규모라
  전부 받아 클라이언트에서 거르는 쪽이 단순하다)
- `name_key` 정규화 정확한 표현식
- 코스 목록 캐싱 여부
- 관리자 편집 폼을 별도 화면으로 띄울지 인라인으로 펼칠지
- 사전 입력 데이터를 스키마 파일에 넣을지 별도 seed 파일로 분리할지
- 추가·수정 후 토스트 문구

## 배포 순서

1. 사용자가 Supabase SQL Editor에서 마이그레이션 실행 (테이블·컬럼·RPC·시드)
2. Claude가 클라이언트 변경을 커밋·푸시
3. 사용자가 대시보드에서 자기 계정의 `is_admin`을 true로 지정
4. 앱에서 확인

1번이 2번보다 먼저여야 한다. 반대로 하면 새 클라이언트가 없는 함수를
호출해 라운드 열기가 실패한다.

## 작성 후 점검에서 정한 것

문서를 빌더 관점으로 다시 읽으며 생긴 질문들. 어느 쪽이든 만들 것이
달라지지 않는 수준이라 Claude가 판단했다. 사용자가 뒤집어도 된다.

- **골프장의 `region`은 권역(북부/중부/남부/기타)이다.** 회원 프로필의
  지역은 성/시 단위(하노이, 박닌…)지만 골프장은 다르게 간다. 목록이
  30개 남짓이라 권역 네 묶음이 선택 화면에서 가장 읽기 쉽다. 성 단위로
  쪼개면 한 묶음에 한두 개짜리 그룹이 잔뜩 생긴다
- **회원은 자기가 추가한 골프장도 수정할 수 없다.** 수정은 관리자만.
  "내가 올린 것만 수정" 규칙은 중복 통합과 충돌하고, 권한 분기가 늘어난다
- **사전 입력 이름은 한글만 쓴다.** 회원이 전부 한국인이고, 영문 병기는
  `name_key` 중복 판정을 어지럽힌다. 영문 검색이 필요해지면 별도 컬럼으로
  나중에 붙인다
- **숨김·통합된 골프장을 쓴 과거 라운드는 그대로 보인다.** `gf_rounds.course`
  이름 스냅샷으로 표시하므로 기록이 사라지지 않는다
- **하루 10개 제한은 `created_by` + `created_at >= now() - interval '1 day'`
  로 센다.** 관리자는 제한에서 제외한다

## 미해결

- 사전 입력 목록을 무엇으로 채울지. 웹 조사로 약 30곳을 확보했으나,
  사용자가 "로얄패밀리 골프동호회" 앱의 코스 목록을 줄 수 있다고 했다.
  그쪽이 실제 동호회 이용 코스라 더 정확하다. 받으면 그것으로 대체하고,
  못 받으면 조사분으로 간다. 어느 쪽이든 설계의 다른 부분은 바뀌지 않는다
